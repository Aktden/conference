# Замеры производительности

Среда: Linux x86_64; Python 3.12.14; loopback HTTP; 13 participants; 4 sections. Использовано постоянное HTTP-соединение авторизованного клиента. По 100 последовательных запросов, concurrency=1. Измерялось полное время ответа клиента по perf_counter.

| Маршрут | Запросов | Медиана мс | p95 мс | Максимум мс | Ошибки |
|---|---|---|---|---|---|
| /api/health | 100 | 2.83 | 6.17 | 10.26 | 0 |
| /api/participants | 100 | 3.76 | 6.19 | 10.94 | 0 |
| /api/participants?search=Морозова | 100 | 3.61 | 7.33 | 12.75 | 0 |

Данные: evidence/logs/performance.json. Отдельный UI-прогон зафиксировал Navigation Timing в ui-report.json. Lighthouse и промышленный нагрузочный тест не запускались.

При этих малых объёмах все 300 запросов завершились успешно. Разница между маршрутом health и чтением участников объяснима работой авторизации и SQLite, но точная причина вариаций не профилировалась. Эти числа не переносятся на внешний сервер или сотни одновременных пользователей. Для масштабирования нужны отдельные нагрузочные сценарии и контроль CPU, памяти, задержек и ошибок.
