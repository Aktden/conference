# Инцидент SQLite при параллельной регистрации

## Проблема

Регистрация одновременно из двух потоков иногда приводила к sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread. Пользователь мог получить ошибку вместо корректной записи или сообщения о заполненной секции.

## Воспроизведение и диагностика

В первой переработанной версии (commit 280c036) тест test_parallel_capacity создаёт секцию на одно место и отправляет две регистрации параллельно. Фактический упавший прогон сохранён в evidence/logs/concurrency-before.xml. Проверены стек вызовов, Depends(get_db), database.connect и BEGIN IMMEDIATE. FastAPI выполняет синхронные dependency/endpoint в пуле потоков; единственное соединение запроса может последовательно использоваться разными рабочими потоками.

## Исправление

В commit e8a85b7 соединение открывается с check_same_thread=False. Каждому запросу по-прежнему принадлежит отдельное соединение; общего глобального connection нет. Транзакция BEGIN IMMEDIATE сериализует проверку мест и запись, timeout/busy_timeout ограничивают ожидание блокировки. Ошибка не скрывается общей обработкой исключений.

## Проверка

Ожидаются ровно 201 и 409 для двух запросов на одно место. Итоговые проверки API проходят; полный вывод — evidence/logs/check.txt. Браузерный сценарий регистрации и отметки посещения подтверждён ui-report.json. Архив отдельно распакован и перезапущен, данные сохранены.
